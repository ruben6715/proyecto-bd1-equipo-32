## 1. Aporte realizado
En esta etapa me encargué de implementar la auditoría de precios de productos en FarmaBlue. Creé la tabla `auditoria_producto`, que guarda la fecha, el usuario que hizo el cambio, el producto afectado, el precio anterior, el precio nuevo y el tipo de operación. Después armé el trigger sobre la tabla de productos para que cada vez que se modifica un precio se inserte automáticamente un registro en esa tabla. Para terminar, hice una prueba: modifiqué el precio de un producto y consulté la auditoría para confirmar que el cambio quedaba registrado.

## 2. Decisiones en las que participé
- Decidimos que la auditoría se haga con un trigger en la base y no desde la aplicación, así queda registrado cualquier cambio de precio sin importar de dónde venga.
- Definí qué datos guardar en cada registro de auditoría (quién, cuándo, qué producto, precio viejo y nuevo, y qué operación se hizo) para poder reconstruir la historia de precios de un producto.

## 3. Problemas o dificultades identificadas
- Al principio no tenía claro cómo obtener el precio anterior y el nuevo dentro del trigger, hasta que entendí cómo funcionan las tablas `inserted` y `deleted` en SQL Server.
- Había que tener en cuenta que un UPDATE puede afectar varias filas a la vez, y que el trigger se ejecuta una sola vez por sentencia y no por cada fila.
- También dudé de qué hacer cuando el UPDATE no cambiaba el precio (por ejemplo, si se modificaba otro campo).

## 4. Soluciones o propuestas realizadas
- Usé `inserted` y `deleted` haciendo un JOIN por la clave del producto, así el trigger registra una fila de auditoría por cada producto modificado, aunque el UPDATE toque varios a la vez.
- Agregué una condición para que solo se audite cuando el precio realmente cambió.
- Para el usuario usé `SUSER_SNAME()` y para la fecha `GETDATE()`, así se completan solos al momento de la operación.
- Probé el trigger con un UPDATE de precio y revisé la tabla de auditoría con un SELECT.
